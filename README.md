# Meridian PT — Interactive 3D Anatomy Experience

A premium physiotherapy website built around a scroll-controlled, real-time
3D skeleton. Next.js 14 (App Router) + TypeScript + Tailwind + React Three
Fiber + GSAP ScrollTrigger + Lenis.

## Getting started

```bash
npm install
npm run dev
```

Then open http://localhost:3000. The site ships with a detailed,
anatomically-proportioned procedural skeleton at
`public/models/skeleton.glb` (173 named bones, generated by
`scripts/generate_skeleton_glb.py` — re-run it any time with
`python3 scripts/generate_skeleton_glb.py`).

To preview with the coarse dev-only primitive rig instead, set
`NEXT_PUBLIC_USE_PLACEHOLDER_SKELETON=true` in `.env.local`.

Before shipping, run:

```bash
npm run lint
npm run typecheck
npm run build
```

## 2. Dependencies installed

`@react-three/fiber`, `@react-three/drei`, `three`, `gsap` (ScrollTrigger),
`@studio-freight/lenis`, plus the standard Next.js/Tailwind/TypeScript
toolchain. Nothing else — no UI kit, no animation library beyond GSAP, no
state manager (the scroll store is ~30 lines, see below).

## 3. The bundled skeleton.glb

`public/models/skeleton.glb` is a detailed, anatomically-proportioned
procedural skeleton (~1.78 m tall, feet at y = 0, facing +Z): skull with
mandible, 24 vertebrae + sacrum, 12 swept rib pairs + sternum,
clavicles/scapulae, full arm/hand bones (humerus, radius, ulna, carpals,
metacarpals, phalanges), pelvis, and full leg/foot bones down to the toes —
173 meshes in total.

Every mesh is named to match the `ANATOMY_KEYWORDS` classifier, so all 173
classify into an anatomy group with zero unassigned. Meshes in groups whose
section sets `separate: true` also carry a `separationOffset` node extra
(a unit direction vector) that `AnatomyController.tsx` uses for the
exploded-joint effect.

Regenerate it any time:

```bash
python3 scripts/generate_skeleton_glb.py   # needs numpy only
```

The script self-verifies at build time: every triangle's winding is checked
outward-facing (face normal vs. analytic vertex normals) and every mesh
name is checked against the classifier. To swap in a scanned/licensed
anatomical model later, drop it at the same path — no code changes needed
as long as its mesh names match the keyword table (or pass `overrides` to
`<SkeletonModel />`).

## 4. How the anatomy regions are mapped

`components/anatomy/anatomyMapping.ts` walks the loaded GLB's scene graph
and buckets every mesh into one of eleven groups (`skull`, `spine`,
`ribCage`, `shoulder`, `arm`, `hand`, `pelvis`, `hip`, `knee`, `ankle`,
`foot`) by testing each mesh's name against a table of regex keyword
patterns (`ANATOMY_KEYWORDS`) tuned for common anatomical-model naming
conventions (Sketchfab/BioDigital-style exports). If your model uses
different names, you have two options, both without touching the
classifier logic elsewhere:

1. Extend `ANATOMY_KEYWORDS` with more patterns, or
2. Pass an `overrides` prop into `<SkeletonModel overrides={{ skull: ["Bip01_Head"] }} />`
   with exact mesh names — overrides always win over keyword matching.

Meshes that match nothing still render (so an unlabeled model never
breaks), they simply won't participate in region-specific highlighting.
In development, unclassified mesh names are logged to the console so you
can see exactly what to add.

## 5. How the scroll timeline works

`AnatomyExperience.tsx` renders one tall section (`ANATOMY_TRACK_VH` = 850vh
by default, in `anatomyData.ts`) containing a `position: sticky` canvas.
A single `ScrollTrigger` measures how far the user has scrolled through
that tall section (0 → 1) and writes the value into `anatomyStore` — a
~30-line pub-sub object, not React state, specifically so that 60fps scroll
updates don't force a React re-render of the whole tree (Section 18 of the
brief). Deliberately **no `pin` option** is used on the ScrollTrigger: CSS
`position: sticky` already pins the canvas, so ScrollTrigger's only job is
measuring progress, and the browser's native scroll (optionally smoothed by
Lenis) stays fully in control — nothing hijacks the wheel/touch input.

Inside the `<Canvas>`, `AnatomyController.tsx` reads that progress value
every frame (not via React state) and:

- Looks up the active `AnatomySection` from `anatomyData.ts` by progress.
- Interpolates the camera position/look-at target between the *previous*
  and *current* section's keyframes across the current section's local
  progress (smootherstep-eased), then damps the live camera toward that
  target with a frame-rate-independent exponential smoothing factor — this
  is what produces the continuous, non-mechanical dolly motion the brief
  asks for in Section 10.
- Raises the "emphasis" (brightness / opacity / scale) of the active
  section's highlighted bone groups and lowers it for everything else, and
  — for sections marked `separate: true` — nudges the relevant meshes a few
  centimeters from their resting position to reveal joint structure,
  scaled by how "in-focus" the section currently is.

Text (`AnatomyLabels.tsx`) does not re-render every scroll frame. It
subscribes only to *section changes* via `useSyncExternalStore`, so it
re-renders (and GSAP-animates in) only the ~13 times the active section
actually changes across the whole scroll.

## 6. How to change the anatomy text

Edit `components/anatomy/anatomyData.ts`. Each entry in the
`anatomySections` array is a self-contained `AnatomySection` object with
`eyebrow`, `title` (array of lines), `description`, and `keyStructures`
(the small anatomical labels shown when the camera zooms into that
region). Nothing else in the codebase needs to change —
`AnatomyLabels.tsx` renders directly from this data.

## 7. How to change camera positions

Same file. Each section has `cameraPosition: [x, y, z]` and
`cameraTarget: [x, y, z]` (world-space meters). The controller
automatically blends between consecutive sections, so you only ever need
to set *resting* poses, not transitions. If you change the model's real
scale/origin, adjust all the position/target values proportionally (or
wrap the model in a scaling `<group>` in `SkeletonModel.tsx` instead of
touching every keyframe).

## 8. How to change animation timing

- **Section boundaries / pacing**: adjust `start`/`end` (0..1 fractions) on
  each `AnatomySection` in `anatomyData.ts`. They must stay contiguous and
  ascending for the timeline math to behave.
- **Overall scroll length**: `ANATOMY_TRACK_VH` in `anatomyData.ts` (850vh
  default — roughly matches the brief's 700–1000vh recommendation).
- **Camera smoothing/damping feel**: the `damp` calculation in
  `AnatomyController.tsx`'s `useFrame` (`1 - Math.pow(0.001, delta)` for
  position, `0.0005` base for bone-emphasis lerps — lower exponent base =
  snappier, higher = more languid).
- **Text enter/exit feel**: the GSAP tween in `AnatomyLabels.tsx`.

## 9. Accessibility & reduced motion

`prefers-reduced-motion: reduce` is checked in four places:
`lib/scroll.ts` (skips initializing Lenis smoothing, so scrolling is 1:1
native), `AnatomyController.tsx` (skips camera easing/bone-emphasis
smoothing and snaps directly to each section's resting pose instead),
`Hero.tsx` and `AnatomyLabels.tsx` (skip their GSAP entrance tweens), and
`app/globals.css` (collapses all CSS transitions/animations globally). All
anatomy copy also exists as real DOM text (not canvas-only), the canvas is
`aria-hidden` since its information is duplicated in the DOM, and a
`sr-only` summary describes the whole sequence for screen readers, so no
information is locked inside the 3D animation.

## 10. Known limitations / what's left to verify

- **Procedural, not scanned.** The bundled skeleton is carefully
  proportioned and correctly named, but it is still a stylized procedural
  model — not a medically exact scan. Camera keyframes are tuned for its
  proportions; a replacement asset with a different scale/origin will need
  the keyframes re-tuned (they're all in `anatomyData.ts`).
- **Draco/meshopt decompression**: if you compress `skeleton.glb`, add the
  relevant `@react-three/drei` loader setup (`useGLTF.setDecoderPath` for
  Draco) — not included since the bundled asset is uncompressed.
- **Hero mark is an abstract SVG**, not a live 3D render, so the page only
  pays for a single WebGL context (the anatomy section). This is a
  deliberate performance/quality tradeoff — call it out if you'd rather the
  hero itself hold a lightweight idle-rotating 3D preview instead.
- Desktop-first responsive rules are in place (mobile camera distances are
  not yet distinctly tuned from desktop — currently the same keyframes
  scale visually via the canvas's responsive `fov`/viewport, but a
  dedicated mobile camera pass would tighten framing further).
